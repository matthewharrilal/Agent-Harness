Phil Schmid's analogy: the model is the CPU, the context window is RAM, the harness is the operating system, the agent is the application. You don't run agents without a harness. And the harness alone doesn't decide what work to do — that's the orchestration pipeline. Below, both taxonomies are explored in depth. Here's the map before you dive in:

The Harness Taxonomy (H1–H8)
Industry-standard infrastructure capabilities. The harness does not decide what work to do. It makes it possible to do work at all.
H1 Context Engineering Absorbable
Manages what the model can see right now — compresses old context, injects relevant info, keeps the window useful instead of cluttered. The gatekeeper between memory and reasoning.
The Analogy
RAM management in an OS. The model can only "see" what's in its context window, just like a CPU can only operate on what's in memory. Context engineering is the memory manager — deciding what gets paged in and what gets swapped out. At the seam between providers, this means each provider has its own RAM with no shared bus — context must be explicitly packaged and transferred.
The H/P Line

The Harness Side: Auto-compaction when the window fills, fork mode for isolated subagent contexts, /context command for manual inspection. The infrastructure manages the physical window — how many tokens remain, when to compress, how to isolate parallel workstreams.

The Pipeline Side: When the pipeline routes the 180K-token codebase analysis to Gemini instead of having Claude read it directly, that's a context engineering decision — "preserve Claude's window for precision work by offloading bulk reads." The pipeline decides what goes into each provider's window and what stays out.

The Line: The harness manages the window. The pipeline decides what's worth putting in it.

The Seam Contrast
Single Provider

Monday morning. Claude reads all 47 files in the payment module. 40K tokens consumed. Auto-compaction kicks in by 3 PM. By the time the developer asks about webhook design decisions made at 10 AM, Claude gives a slightly different answer — the original reasoning was compacted away. The window is full and lossy.

Manual Bridge

You open Gemini CLI, manually paste a summary of the 47 files. You wrote ~2K tokens of context. Gemini analyzes, returns findings. You paste those findings back into Claude. Two context windows, manually bridged. You're the context engineer — deciding what each model sees. It works but you're doing the pipeline's job by hand.

Managed Seam

Pipeline routes the 180K-token analysis to Gemini's 1M-token window (P2/P3). Structured 3K summary returned. Claude's window is 97% free. No compaction needed. All reasoning space preserved for building the service. Each provider gets a context window tuned to its task.

The three panels reveal the core context tradeoff: a single provider's window is finite and shared across all work. Two providers' windows are larger in aggregate but disconnected. The managed seam makes them feel like one large, intelligent window.
Pipeline Bleed
Amplifies
P1 Decomposition becomes more effective when it has the full request visible. Better context engineering means decomposition can see the whole task and its dependencies before splitting. P6 Recomposition benefits from available window space — more room means Claude can hold both providers' outputs simultaneously when merging.
Reduces
P2 Classification simplifies when the context is clean. Instead of classifying from a cluttered, compacted window, the classifier sees a crisp task description. Fewer misclassifications, less re-routing.
Stresses
H4 Memory gets pressured. Better context engineering means more demand on memory — when the injection budget is tight (say, 2K tokens from a 200K window), the memory layer's retrieval ranking becomes critical. Context and memory compete for the same window space.
Context and memory are in direct tension. When context engineering improves, it creates more space — but more space means more demand for what to fill it with. The H1/H4 tension is the most important intra-harness dynamic.
The Overlap Zone Context injection is where harness infrastructure meets pipeline curation

The mechanism is auto-compaction, fork mode, token counting, context isolation per subagent.

The policy is deciding that memory injection from H4 gets 800 tokens, the current task description gets 2K tokens, and Gemini's last output summary gets 500 tokens.

They blur when the compaction algorithm starts making curation decisions. When Claude auto-compacts, it decides what to keep and what to discard. That's the harness making a policy choice — "this conversation turn was less important than that one." The harness is curating, which is supposed to be the pipeline's job. In practice, compaction is a low-quality version of what the pipeline's memory injection does deliberately.

Maps to the tool access overlap point: H1 provides the window and compaction; the pipeline decides what to put into it via hook injection and Gemini-to-Claude context packaging.

Evolution Arc One of Claude Code's strongest capabilities — rapidly improving

Implicit Baseline: Auto-compaction, /context command for manual inspection, subagent context isolation via fork mode. High maturity for single-provider context management.

What External Tools Proved: Claude-Flow proved multi-agent context coordination (60+ agents sharing context). PAL MCP proved cross-provider context passing via clink feature. Neither does intelligent cross-provider context optimization.

Being Absorbed: Context engineering is already one of Claude Code's strongest areas. Fork mode, compaction, and subagent isolation are all native and improving rapidly.

Where It's Heading: Context windows keep growing (Claude 200K, Gemini 1M+). As windows grow, raw context management matters less — you can fit more before compaction. But cross-provider context coordination (packaging Claude's context for Gemini, translating Gemini's output for Claude) remains a gap that growing windows don't solve.

Growing context windows reduce the single-provider context problem. They don't solve the cross-provider context problem. When Claude has 500K tokens, it still can't share them with Gemini.
Structural Moat Single-provider fully covered; cross-provider context packaging is moated

Single-provider aspect: ABSORBABLE. Anthropic's context engineering is already best-in-class. Compaction, fork mode, subagent isolation — all native, all improving. No reason to build single-provider context management.

Cross-provider aspect: PARTIAL MOAT. Packaging Claude's ongoing context into a format Gemini can use effectively (and vice versa) is cross-provider work. But the "packaging" is relatively thin — it's summarization and formatting, not deep infrastructure. A sufficiently good prompt template might do 80% of this job. The moat is real but shallow.

What would erode the moat? If both providers adopt a shared context serialization format (e.g., a standard "project context" JSON schema), packaging becomes trivial. MCP's evolution toward richer context sharing could enable this.

Context engineering is the one H capability where single-provider coverage is already strong. Our value isn't in managing Claude's window — it's in bridging two windows intelligently.
Project Reflection

Context engineering is not where we invest heavily. It's already strong natively (HIGH coverage), the single-provider moat doesn't exist, and the cross-provider moat is shallow. What we need is a good context packaging function — "take Claude's current state and summarize it for Gemini" — not a context management system. This is a utility, not a feature. Build it as a helper inside the dispatch flow, not as a standalone layer.

The H1/H4 tension shapes the architecture. Context and memory compete for window space. If we build memory (H4) first, we need a context injection strategy that doesn't bloat the window. The injection budget — how many tokens of memory to inject per prompt — is an architectural decision that should be made early. The 800-token figure from the journey scenario needs real-world testing.

Open question: As context windows grow to 500K+, does the entire "context pressure" problem disappear? If Claude never compacts because the window is big enough, does cross-provider context routing lose its value? The answer depends on task size growing faster than window size — which it historically has (codebases keep getting bigger).

H2 Tool Integration Partial Moat
Gives the agent hands — file operations, code execution, web search, API calls, MCP. Without this, the agent can only talk. The single most critical harness capability: without H2, nothing else functions.
The Analogy
Device drivers in an OS. The model says "read this file" the same way a program calls open(). The harness translates that into actual filesystem operations. Without drivers, the CPU is disconnected from all peripherals. At the seam, this means the pipeline needs a "driver" for Gemini — an MCP tool that spawns, communicates with, and captures output from a different provider's CLI.
The H/P Line

The Harness Side: 170+ built-in tools (Read, Edit, Bash, Grep, Glob, WebFetch), MCP protocol for extensibility, Bash execution, subagent spawning. The raw ability to invoke processes, read files, write output. Claude Code's strongest infrastructure.

The Pipeline Side: Which tool, which model, for which subtask. The pipeline registers a delegate_to_gemini() MCP tool. Claude calls it when the pipeline's logic determines delegation is warranted. The tool itself is infrastructure; the decision to call it is intelligence.

The Line: The harness provides the MCP runtime and process management. The pipeline provides the tools that bridge to other providers.

The Seam Contrast
Single Provider

Claude Code with 170+ tools is powerful within its own ecosystem. Read files, edit code, run tests, search the web. But no tool can invoke Gemini. The pipeline says "send this to Gemini" — but WHO spawns Gemini? "Not my job." WHO captures output? "Not my job." A brain with no hands for cross-provider work.

Manual Bridge

Developer opens a second terminal. Manually types into Gemini CLI. Copy-pastes results back to Claude. The developer IS the tool integration layer — the human process manager spawning Gemini, managing timeouts (waiting for response), capturing output (copy), returning it (paste). Every pipeline step executes, with the human as the harness.

Managed Seam

Claude calls delegate_to_gemini(task, context) — an MCP tool the pipeline registered. The harness spawns the subprocess, passes scoped directory access, manages timeout, captures structured JSON output, returns it to Claude's conversation. The pipeline decided, the harness executed. The developer never saw two terminals.

The manual bridge panel reveals something important: cross-provider work is already possible today — with the developer as the integration layer. The automation question isn't "can we do this?" but "is the human overhead worth automating away?"

Amplifies

P5 Conflict detection and critique become possible — the veto pattern requires file diffs (H2 reads files), spawning Gemini for review (H2 process management), and gating merges (H2 tool control).

Stresses

H2 is the capability where "harness enables, pipeline decides" is most literal. Every P step requires H2 tools to execute. Improving tool integration doesn't just help the pipeline — it makes the pipeline possible at all.
The Overlap Zone The delegate_to_gemini tool is infrastructure that encodes routing policy

The mechanism is MCP protocol, process spawning, stdin/stdout capture, timeout management, JSON parsing of tool outputs.

The policy is which MCP tools to register, what parameters they accept, what structured output they return, how Claude is instructed to use them.

They blur when the MCP tool's implementation encodes routing logic. If delegate_to_gemini() includes retry logic ("if Gemini fails, try again with simplified context"), is that infrastructure (error handling) or policy (when to retry vs. fall back to Claude)? The three-tier reliability model (CLAUDE.md soft steering → hooks hard enforcement → MCP tools capability extension) puts the blur point at Tier 2/3 boundary: hooks always fire (infrastructure), but the hook script's logic is policy.

Project Reflection

Don't reinvent the MCP tool — invest in the reliability layer. PAL MCP already provides cross-provider invocation with 10K+ stars and active maintenance. Our value isn't a better delegate_to_gemini() tool — it's the hooks-based reliability system that ensures delegation happens even when Claude doesn't think to call the tool. The three-tier reliability model (CLAUDE.md steering + hooks enforcement + MCP tools) is our actual contribution to H2.

MCP tool count matters. Research shows that >10% tool definitions in context triggers Tool Search, reducing reliability for any individual tool. Our MCP server should expose 3–5 tools maximum: delegate, query memory, check rate status. Minimal surface area, maximum reliability.

Open question: Should we build on top of PAL MCP's clink feature (already proven, 10K+ stars) or build our own Gemini invocation from scratch? Building on PAL MCP gets us to a working prototype faster but adds a dependency on an external project we don't control.

How does MCP tool invocation reliability interact with Gemini's free tier rate limits? If Gemini's free tier has its own rate limits, the delegation tool needs to handle that gracefully — cascading rate limits across providers.

H3 State & Session Persistence Partial Moat
Keeps track of where things stand across time — progress files, checkpoints, recovery points, usage counters. Work survives restarts. The pipeline's rate prediction depends entirely on H3's counters.
The Analogy
The filesystem and process table in an OS. When a program crashes, the OS can restart it and the filesystem still has the data. State persistence means the agent's work isn't lost when something goes wrong. At the seam, this means tracking state that spans both providers — which subtask went to which model, what's in progress, what completed.
The H/P Line

The Harness Side: Git provides file-level persistence. Sessions maintain in-conversation state. TaskCreate tracks subtasks with dependencies. PostToolUse hooks can increment counters on every tool call. The infrastructure writes, reads, and maintains state files.

The Pipeline Side: The PostToolUse hook increments a rate counter (infrastructure). The prediction model calculates "Claude exhausts at 5:30 PM based on current burn rate of 12K tokens/hour" and recommends delegating boilerplate subtasks to Gemini (intelligence). The policy of when to checkpoint, what constitutes a recovery point, and how to interpret usage counters — that's pipeline logic riding on state infrastructure.

The Line: The harness stores and updates counters. The pipeline interprets them and acts.

The Seam Contrast
Single Provider

Monday 6:30 PM. Rate limit hits with no warning. Developer is mid-task on the webhook handler. Session state (task list, partial edits) exists in the terminal but no persistent counter tracked burn rate. No mechanism predicted the wall. Developer switches to Gemini manually — but Gemini has no knowledge of Claude's task state.

It works but relies on human memory and discipline.

At 3 PM, proactive delegation of boilerplate subtasks to Gemini. The state layer tracked, the pipeline predicted, the developer never hit the wall. Cross-provider task state is maintained automatically.

The manual bridge panel shows that state persistence is already possible with human discipline. The managed seam replaces that discipline with infrastructure — converting "remember to check your usage" into "the system tracks and predicts for you."

Project Reflection

H3 and H4 should probably be one system. The boundary between "within-session state" (H3) and "cross-session memory" (H4) is artificial for our use case. Cross-provider task tracking ("Gemini handled subtask 3") is both state (active right now) and memory (needed tomorrow). Building them as separate systems means either duplicating storage or defining a complex migration policy for when state becomes memory. A unified persistence layer with different retention policies (ephemeral vs. permanent) is simpler.

Rate tracking feeds the on-ramp. Proactive rate prediction is the overflow scenario's trigger mechanism — the first moment where the system adds value over "just use Claude until limited." This means H3 rate counters + P7 prediction are the MVP's trigger, even if memory (H4) is the MVP's core. Build the counter infrastructure early; the prediction logic can start simple (linear burn rate) and get sophisticated later.

Open question: Is PostToolUse hook the right instrumentation point for rate tracking? It fires on every tool call, but token consumption doesn't correlate 1:1 with tool calls (a single Bash command might use 50 tokens or 5,000). The counter might need to track conversation turns or estimated token ranges, not tool invocations.

Open Threads

What's the right granularity for rate tracking? Per-tool-call? Per-conversation-turn? Per-minute? The Usage Monitor uses P90 percentile statistics on weekly resets, but our prediction needs within-session granularity.

Can cross-provider state be derived from git history instead of tracked separately? If Gemini's edits are committed with provider attribution, git log becomes the state record. Simpler infrastructure but less structured for querying.

H4 Memory Partial Moat
Persistent storage and retrieval of project knowledge across sessions — what to remember, what to forget, how to find the right memory at the right time. The pipeline's most important capability depends on the harness's weakest infrastructure.
The Analogy
Long-term storage with an index. RAM (context window) is fast but volatile. Disk (memory) is persistent. But a raw filesystem without search is useless — you need an index (semantic retrieval) to find the right memories at the right time. At the seam between providers, this means neither Claude nor Gemini can remember what the other did — unless something stores and indexes those cross-provider decisions.
The H/P Line

The Harness Side: SQLite-vec with 384-dimensional embeddings, sub-15ms retrieval, ONNX runtime for local embedding generation. The infrastructure stores vectors, runs similarity searches, persists to disk, handles concurrent reads. This is plumbing — it doesn't know what it's storing or why.

The Pipeline Side: Monday's webhook race condition fix is worth remembering but the intermediate debugging steps aren't. The pipeline decides that Gemini's discovery of a missing API endpoint (process_refund_with_metadata) should be tagged as a BLOCKER and stored at high priority, while the 14 routine file reads that led to the discovery are discarded. Curation, retrieval policy, cross-provider attribution — all intelligence.

The Line: The harness stores and retrieves. The pipeline curates.

Project Reflection

Memory is the build-order lynchpin. The moat analysis says cross-provider memory is durable and single-provider memory is absorbable. The bleed analysis says routing quality depends on memory history. The evolution arc says Anthropic will ship single-provider memory within 6–12 months. Taken together: our memory layer should be built cross-provider from day one — not as a single-provider system we later extend. If we build single-provider memory first, Anthropic absorbs it before we get to the cross-provider part. If we build cross-provider memory first, we have something durable from the start, and Anthropic's native memory becomes our foundation rather than our competitor.

The Overlap Zone P7 is where harness and pipeline blur the most — mechanism and policy are entangled

P7 is partially harness, partially pipeline — it's where the two blur the most. Three sub-capabilities, each split:

  • Rate: Tracking (counting tokens, storing counters) = H3. Prediction (modeling burn rate, forecasting exhaustion) = pipeline. Decision (route to Gemini based on prediction) = pipeline.
  • Memory: Storage (SQLite-vec, embeddings, retrieval) = H4. Curation (what's worth remembering, what to inject, decay policies) = pipeline.
  • State: Persistence (files, checkpoints) = H3. Policy (when to checkpoint, what constitutes recovery) = pipeline.

The blur is so deep that P7 could be decomposed into three separate capabilities. But grouping them captures an important truth: rate, memory, and state are the same persistence layer viewed from different temporal perspectives (present, past, recovery). They should share infrastructure.

Pipeline-to-Pipeline Tensions Rate management is the on-ramp; memory is the foundation

P7's three sub-capabilities are in tension with each other: rate management (the overflow trigger) is the most immediately valuable but the most fragile (if Anthropic doubles capacity, it matters less). Memory (cross-session continuity) is the most durably valuable but requires the most infrastructure investment. State (recovery/checkpointing) is the least visible to users but critical for reliability.

Build order tension: rate management is the on-ramp (immediate pain relief) but memory is the foundation (enables everything else). Build memory first or rate first? The project plan says rate is the trigger for the overflow scenario, but H4's analysis says memory should come first because the router needs routing history.

Structural Moat Rate tracking absorbable; cross-provider memory/state moated

Project Reflection

P7 is the project in miniature. Rate management is the user's pain point (the on-ramp). Memory is the technical foundation (everything depends on it). State is the reliability layer (work survives crashes). The three sub-capabilities of P7 are roughly the three phases of the project: Phase 1 = rate awareness + overflow. Phase 2 = memory + context continuity. Phase 3 = recovery + reliability.

The H4 Project Reflection's conclusion applies here: Build memory before routing. P7's rate prediction is more accurate with routing history from memory. P7's memory curation is useful from day one (even without a router). The build order: memory curation → rate tracking → rate prediction → routing decision. Each step adds a layer of intelligence on top of the previous one's data.

The project's on-ramp depends on rate pain being real. If the pain shrinks, does the project's entry point shift from "overflow when rate-limited" to "cross-provider memory for context continuity"? That's a different pitch with different urgency.

The Scope Principle
